# channels/

Every directory in here that contains a `.env` is **one 24/7 YouTube stream**,
with its own playlist, image set, visualisation, colour profiles and schedule.
Channels run independently — starting, stopping or restarting one does not
touch the others.

## Adding a stream

```bash
mkdir -p channels/lofi/{audio,images}
cp channels/example/.env.example channels/lofi/.env
chmod 600 channels/lofi/.env
```

Then edit `channels/lofi/.env` and paste that stream's YouTube key into
`YOUTUBE_STREAM_KEY`. Each stream needs its **own** key — create one per
YouTube channel in Studio (Go Live → Stream → Select stream key → reusable).

## Where media comes from

A channel draws from two places, and can mix them freely:

| Source | Scope |
|---|---|
| `common/audio`, `common/images` | shared by every channel — stored once |
| `channels/<name>/audio`, `channels/<name>/images` | this channel only |

Put anything reused across streams in `common/` rather than copying it per
channel. Being in `common/` makes a file *available* to a channel, not
automatically used — each channel selects what it wants in its `config.yaml`.
See [common/README.md](../common/README.md).

Both trees are read live: adding or removing files does not restart anything.

Repeat for each stream you want. Supported range is 1–8.

## Layout

```
common/                   <- shared by every channel, stored once
├── audio/
├── images/
└── profiles/

channels/
├── example/              <- template, not a running stream (no .env)
│   └── .env.example
├── lofi/                 <- a stream
│   ├── .env              <- stream key + per-stream overrides   (gitignored)
│   ├── config.yaml       <- selection, visualisation, schedule  (gitignored)
│   ├── audio/            <- music for THIS channel only         (gitignored)
│   ├── images/           <- images for THIS channel only        (gitignored)
│   ├── profiles/         <- colour profiles for this channel's images
│   ├── playlist.m3u      <- generated from config.yaml; spans common + channel
│   ├── images.list       <- generated from config.yaml; spans common + channel
│   └── docker-compose.yml <- generated by the backend; do not hand-edit
└── nature/               <- another stream, entirely independent
    └── ...
```

`example/` is deliberately not a stream — it has no `.env`, so nothing starts
from it. Copy it, don't run it.

## What lives where

| Setting | File |
|---|---|
| YouTube stream key | `channels/<name>/.env` |
| Resolution, fps, encoder, CPU/memory limits | `channels/<name>/.env` |
| Icecast mount names | `channels/<name>/.env` |
| Which common + channel media this stream uses, and in what order | `channels/<name>/config.yaml` |
| Visualisation, presets, schedule | `channels/<name>/config.yaml` |
| Ports, host paths, Icecast credentials, backend auth | the root `.env` |

The split is deliberate: `.env` holds secrets and things Docker needs at
container-creation time, `config.yaml` holds everything the backend can change
on a running stream without restarting it.

## Capacity

Measured on a running 7-core host: roughly **1.5 cores per 720p stream** with
one visualisation plugin loaded. Reserve about a core for the OS and the shared
services, then divide — roughly four streams on that host.

That is higher than filtergraph benchmarks alone predict, because the HLS
preview is a second encode rather than a free tap off the first. See the
capacity section of [docs/architecture.md](../docs/architecture.md).

## Never commit

`.env`, `config.yaml`, `audio/`, `images/` and `profiles/` are all gitignored.
A stream key grants publish rights to your YouTube channel — treat
`channels/*/.env` like a password file (`chmod 600`).
